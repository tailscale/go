# Go bugs.

# The server initializes each stream's receive window to its configured
# MaxReceiveBufferPerStream as soon as it sends SETTINGS, so data a
# client sends under the default 65535-byte window before receiving
# the server's SETTINGS is reset with RST_STREAM FLOW_CONTROL_ERROR.
# RFC 9113 §6.9.3 permits this ("the receiver MAY instead send a
# RST_STREAM with an error code of FLOW_CONTROL_ERROR for the affected
# streams"; requirement 9113-6.9.3-3), but clients don't retry such
# requests, so they fail. Accepting the data, which §6.9.3 also
# permits, would interoperate better. Only configurations with
# MaxReceiveBufferPerStream < 65535 (the "constrained" profile) are
# affected; whether a client sends early depends on the client and on
# timing. (conform/server/early-data-before-settings warns.)
gogo:constrained/*/upload-* FLAKY
gogo:constrained/*/echo-1m FLAKY
gogo:constrained/*/concurrent-upload-20 FLAKY
goserver:constrained/*/upload-100k FLAKY
goserver:constrained/*/upload-10m FLAKY
goserver:constrained/*/upload-stream FLAKY
goserver:constrained/*/echo-1m FLAKY
goserver:constrained/*/concurrent-upload-20 FLAKY
goserver:constrained/h2load/*/uploads FLAKY

# Go bug: the client can open a stream exceeding a newly lowered
# SETTINGS_MAX_CONCURRENT_STREAMS after acknowledging the SETTINGS
# (RFC 9113 §5.1.2): a request takes a concurrency slot under the old
# limit, then the read loop applies the new limit and writes the ACK
# before the request's HEADERS are written. Servers may treat this as a
# connection error (nghttp2-based servers do, failing every request on
# the connection) or a stream error with PROTOCOL_ERROR (the Go server
# does), which the client doesn't retry.
#
# Go bug: similarly, the client can send DATA exceeding a newly lowered
# SETTINGS_INITIAL_WINDOW_SIZE after acknowledging it: awaitFlowControl
# takes flow control credit before the read loop applies the SETTINGS
# and writes the ACK, and the DATA is written after the ACK.
gogo:constrained/*/concurrent-* FLAKY
goclient*/*:constrained/*/concurrent-* FLAKY
goclient*/*:constrained/*/upload-* FLAKY
goclient*/*:constrained/*/echo-1m FLAKY

# Go bug: if the response headers arrive while the request body is
# still blocked on flow control, nothing watches the request's context:
# the body-writing goroutine waits in awaitFlowControl on cc.cond, and
# the context.AfterFunc set up by clientStream.detach only exists once
# the body has been sent. Cancellation or a deadline then never ends
# the request, and reading the response body blocks forever.
conform/client/context-deadline-during-body-write FAIL

# Go bug: the server rejects HTTP/2 over TLS older than 1.2 and over
# prohibited TLS 1.2 cipher suites (serverConn.serve), but the client
# doesn't check: if tls.Config.MinVersion permits TLS 1.0 or 1.1 and
# the server negotiates it with ALPN h2, the client speaks HTTP/2 over
# it (RFC 9113 §9.2: MUST use TLS 1.2 or higher). (It also uses
# prohibited cipher suites, which §9.2.2 says SHOULD NOT happen;
# conform/tls/client/prohibited-cipher-suites warns.)
conform/tls/client/tls-version FAIL

# Go bug: after the client acknowledges a smaller
# SETTINGS_HEADER_TABLE_SIZE, the server accepts a field block that
# doesn't start with a dynamic table size update (RFC 9113 §4.3.1:
# MUST be a COMPRESSION_ERROR). processSettings just shrinks the
# decoder's table, so the tables silently diverge and a later block
# fails with COMPRESSION_ERROR. (HAProxy's encoder does this.)
conform/server/hpack-table-reduction-without-update FAIL

# Go bug: trailers that the client sent on a stream the server had
# already reset are treated as a connection error (PROTOCOL_ERROR,
# "stream_went_down") rather than discarded (RFC 9113 §5.1, §6.4).
conform/server/reset-stream-trailers-discarded FAIL

# Go bug: on an established CONNECT tunnel, the server accepts a
# HEADERS frame with END_STREAM as trailers (RFC 9113 §8.5: frames

conform/server/connect-tunnel-headers FAIL

# Go bug: the server doesn't limit the number of idle streams

# Go bug: the client limits its HPACK decoder's dynamic table to
# MaxDecoderHeaderTableSize as soon as it's created, rather than when

# then using the default 4096-byte table fail with COMPRESSION_ERROR.

conform/client/hpack-table-size-before-settings-ack FAIL

# Go bug: the client delivers DATA sent in 204 and 304 responses as

# The server, like the client, sends a connection and a stream
# WINDOW_UPDATE for every 32KB a handler reads, about 60 per 1MB DATA
# frame (RFC 9113 §6.9.1 advises against very small increments;
# conform/server/window-update-rate warns).

# Go bug: the client sends a WINDOW_UPDATE for the connection and the
# stream every time the application reads at least 4KB
# (inflowMinRefresh), regardless of the peer's DATA frame size, while
# advertising SETTINGS_MAX_FRAME_SIZE of 1MB. Envoy's default flood
# protection (max_inbound_window_update_frames_per_data_frame_sent)
# closes connections that receive many more WINDOW_UPDATE frames than
# the DATA frames it sent, so large downloads from Envoy fail. Whether
# Envoy sends large DATA frames depends on timing;
# conform/client/window-update-rate measures the rate directly.
