# h2interop peers

Each subdirectory here is a Docker build context for one or more peer
HTTP/2 implementations used by h2interop. The directories are
embedded in the h2interop binary, and images are built automatically,
tagged with a hash of the directory contents, so editing a file here
causes an image rebuild the next time h2interop is built and run.

All containers run with `--network=host`, with a read-only directory
mounted at `/work` containing:

- `/work/cert.pem`, `/work/key.pem`: the test certificate and key
  (from net/http/internal/testcert; valid for 127.0.0.1 and example.com).
- `/work/htdocs/`: static files for static file servers:
  `hello`, and `bytes/N` for the sizes in `staticSizes` (docker.go).
- `/work/conf/`: configuration files generated by h2interop
  for servers configured by file (nginx, etc).

## Library peers

Library-based peers (Python h2, Node.js, Rust h2, Java) implement a
small JSON protocol so the runner can drive them uniformly. An image
may provide either or both of these executables in `$PATH`:

### `client`

Run as `client` with a ClientSpec JSON document on stdin.
It must write a ClientOutput JSON document to stdout. Logs go to stderr.
Exit status 0 even if requests fail (report failures in the output).

ClientSpec:

```json
{
  "url": "https://127.0.0.1:1234",   // base URL; https => TLS+ALPN h2, http => h2c
  "h2c": true,                        // speak HTTP/2 with prior knowledge over cleartext
  "authority": "",                    // if non-empty, send this :authority instead of host:port
  "concurrent": false,                // true: issue all requests at once on ONE connection;
                                      // false: issue sequentially on ONE connection
  "requests": [{
    "method": "POST",
    "path": "/upload?x=1",            // appended to url as-is (already encoded)
    "header": [["x-foo", "bar"]],     // extra request fields, in order; may repeat names
    "body_len": 1000,                 // send Pattern(body_len) as the body; 0 = no body
    "no_content_length": false,       // if true, don't send content-length (stream the body)
    "trailer": [["x-t", "v"]],        // send these request trailers after the body
    "expect_continue": false,         // send expect: 100-continue, wait for 100 before body
    "cancel_after": 0                 // if > 0: reset the stream (RST_STREAM CANCEL) after
                                      // receiving at least this many response body bytes
  }]
}
```

TLS clients must not verify the server certificate (or must trust
/work/cert.pem), must offer ALPN "h2", and should send no SNI or
any SNI.

Only one connection should be used: requests must be multiplexed
when `concurrent` is true, and the connection reused when false.
(A client may open more connections if the server's
SETTINGS_MAX_CONCURRENT_STREAMS requires it.)

ClientOutput:

```json
{
  "results": [{                       // one per request, in the same order
    "status": 200,
    "proto": "h2",                    // if known
    "header": [["content-type", "text/plain"]],  // response fields, lowercase names, excluding pseudo-headers
    "trailer": [["x-trailer-a", "1"]],
    "informational": [{"status": 103, "header": [["link", "..."]]}],  // 1xx responses
    "body_len": 1000,
    "body_sha256": "hex",
    "body": "...",                    // the body, if valid UTF-8 and <= 64KiB
    "error": "",                      // non-empty if the request failed (e.g. stream reset)
    "canceled": false                 // true if the client canceled per cancel_after
  }],
  "error": ""                         // fatal error that prevented running requests
}
```

### `server`

Run as `server '<ServerSpec JSON>'` (the spec is the first argument).
It must listen on `addr` and serve the route set below until killed.

```json
{
  "addr": "127.0.0.1:1234",
  "tls": true,                        // TLS with ALPN "h2" (and only h2); false => h2c prior knowledge
  "cert": "/work/cert.pem",
  "key": "/work/key.pem",
  "settings": {"SETTINGS_MAX_CONCURRENT_STREAMS": 4}  // optional; apply those supported
}
```

## The body pattern

`Pattern(n)` is n bytes where byte i is `ALPHABET[i % 63]`, with

    ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ\n"

`headerPattern(n)` is n bytes where byte i is
`"abcdefghijklmnopqrstuvwxyz0123456789"[i % 36]`.

## The route set

Servers serve these routes. Unless stated, responses are 200, and
any method is accepted. The reference implementation is `routeHandler`
in routes.go.

| Route | Response |
|---|---|
| `/hello` | body `Hello, HTTP/2 interop!\n`, content-type text/plain, with content-length |
| `/bytes/{n}` | body Pattern(n), with content-length n (also for HEAD, with no body) |
| `/stream/{n}` | body Pattern(n) without content-length, written in 1000-byte chunks, each flushed as its own DATA frame |
| `/echo` | response body is the request body, streamed back as it arrives (full duplex); content-length = request content-length if known |
| `/upload` | reads the whole request body, responds with JSON `{"len": N, "sha256": "hex", "trailer": {"name": ["v"]}, "content_length": N or -1}` (`trailer` omitted if none; names lowercase) |
| `/trailers` | body `trailers follow\n`, then trailers `x-trailer-a: 1` and `x-trailer-b: two` |
| `/status/{code}` | status `code`, empty body |
| `/bigheader/{n}` | header `x-big: headerPattern(n)`, body `ok\n` |
| `/manyheaders/{n}` | headers `x-h-0: value-0` ... `x-h-{n-1}: value-{n-1}`, body `ok\n` |
| `/early-hints` | a 103 response with `link: </style.css>; rel=preload; as=style`, then 200 with body `ok\n` |
| `/info` | JSON `{"method": "GET", "path": "/info?q", "authority": "host:port", "header": {"name": ["v1", "v2"]}}`: path is the :path including query; authority is :authority (or host); header excludes pseudo-headers, names lowercase, values in order received (cookie crumbs may be joined or not) |
| `/delay/{ms}` | waits ms milliseconds, then body `ok\n` |
| `/rst` | sends headers and 1000 bytes of Pattern, then resets the stream with RST_STREAM (INTERNAL_ERROR) |

`/upload` must report request trailers whether or not the request
declared them in a `Trailer` field.

Content-type is not checked except where stated.
