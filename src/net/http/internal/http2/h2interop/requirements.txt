# Normative requirements of the HTTP/2 RFCs, for tracking test coverage.
#
# This file lists every sentence containing a BCP 14 keyword in
# RFC 9113 (HTTP/2), RFC 7541 (HPACK), RFC 9218 (Extensible
# Priorities, HTTP/2 parts), and RFC 8441 (Extended CONNECT). Each entry
# is
#
#	<id> <keywords> §<section> <section title>
#		<text>
#		[n/a <role>: <reason>]...
#
# where <id> is <rfc>-<section>-<n>. Requirements bind the Go client,
# the Go server, or both ("roles"). Tests, validator checks, and h2spec
# cases declare which requirement IDs they cover (search the source for
# the ID). A role that no test covers must have an "n/a" line saying
# why it can't or needn't be tested. Run h2interop -requirements to see
# the coverage of each requirement; TestRequirements fails if any role
# of any requirement is neither covered nor marked n/a.
#
# Quoted text is from the RFCs, Copyright (c) IETF Trust and the
# persons identified as the document authors. All rights reserved.

9113-3.2-1 MUST_NOT §3.2 Starting HTTP/2 for "https" URIs
	The "h2c" protocol identifier MUST NOT be sent by a client or
	selected by a server; the "h2c" protocol identifier describes a
	protocol that does not use TLS.

9113-3.2-2 MUST §3.2 Starting HTTP/2 for "https" URIs
	Once TLS negotiation is complete, both the client and the server
	MUST send a connection preface (Section 3.4).

9113-3.3-1 MUST §3.3 Starting HTTP/2 with Prior Knowledge
	HTTP/2 connections over TLS MUST use protocol negotiation in TLS
	[TLS-ALPN].

9113-3.3-2 MUST §3.3 Starting HTTP/2 with Prior Knowledge
	Likewise, the server MUST send a connection preface (Section 3.4).
	n/a client: requirement on servers

9113-3.4-1 MAY,MUST §3.4 HTTP/2 Connection Preface
	This sequence MUST be followed by a SETTINGS frame (Section 6.5),
	which MAY be empty.
	n/a server: requirement on clients

9113-3.4-2 MUST §3.4 HTTP/2 Connection Preface
	The server connection preface consists of a potentially empty
	SETTINGS frame (Section 6.5) that MUST be the first frame the
	server sends in the HTTP/2 connection.
	n/a client: requirement on servers

9113-3.4-3 MUST §3.4 HTTP/2 Connection Preface
	The SETTINGS frames received from a peer as part of the connection
	preface MUST be acknowledged (see Section 6.5.3) after sending the
	connection preface.

9113-3.4-4 MUST §3.4 HTTP/2 Connection Preface
	Clients and servers MUST treat an invalid connection preface as a
	connection error (Section 5.4.1) of type PROTOCOL_ERROR.

9113-3.4-5 MAY §3.4 HTTP/2 Connection Preface
	A GOAWAY frame (Section 6.8) MAY be omitted in this case, since an
	invalid preface indicates that the peer is not using HTTP/2.
	n/a client: permission (MAY); there is no behavior to require
	n/a server: permission (MAY); there is no behavior to require

9113-4.1-1 MUST_NOT §4.1 Frame Format
	Values greater than 2^14 (16,384) MUST NOT be sent unless the
	receiver has set a larger value for SETTINGS_MAX_FRAME_SIZE.

9113-4.1-2 MUST §4.1 Frame Format
	Implementations MUST ignore and discard frames of unknown types.

9113-4.1-3 MUST §4.1 Frame Format
	Unused flags MUST be ignored on receipt and MUST be left unset
	(0x00) when sending.

9113-4.1-4 MUST §4.1 Frame Format
	The semantics of this bit are undefined, and the bit MUST remain
	unset (0x00) when sending and MUST be ignored when receiving.

9113-4.2-1 MUST §4.2 Frame Size
	All implementations MUST be capable of receiving and minimally
	processing frames up to 2^14 octets in length, plus the 9-octet
	frame header (Section 4.1).

9113-4.2-2 MUST §4.2 Frame Size
	An endpoint MUST send an error code of FRAME_SIZE_ERROR if a frame
	exceeds the size defined in SETTINGS_MAX_FRAME_SIZE, exceeds any
	limit defined for the frame type, or is too small to contain
	mandatory frame data.

9113-4.2-3 MUST §4.2 Frame Size
	A frame size error in a frame that could alter the state of the
	entire connection MUST be treated as a connection error (Section
	5.4.1); this includes any frame carrying a field block (Section
	4.3) (that is, HEADERS, PUSH_PROMISE, and CONTINUATION), a
	SETTINGS frame, and any frame with a stream identifier of 0.

9113-4.3-1 MUST §4.3 Field Section Compression and Decompression
	Field blocks MUST be transmitted as a contiguous sequence of
	frames, with no interleaved frames of any other type or from any
	other stream.

9113-4.3-2 MUST §4.3 Field Section Compression and Decompression
	A receiver MUST terminate the connection with a connection error
	(Section 5.4.1) of type COMPRESSION_ERROR if it does not
	decompress a field block.

9113-4.3-3 MUST §4.3 Field Section Compression and Decompression
	A decoding error in a field block MUST be treated as a connection
	error (Section 5.4.1) of type COMPRESSION_ERROR.

9113-4.3.1-1 MUST §4.3.1 Compression State
	Once an endpoint acknowledges a change to
	SETTINGS_HEADER_TABLE_SIZE that reduces the maximum below the
	current size of the dynamic table, its HPACK encoder MUST start
	the next field block with a Dynamic Table Size Update instruction
	that sets the dynamic table to a size that is less than or equal
	to the reduced maximum; see Section 4.2 of [COMPRESSION].

9113-4.3.1-2 MUST §4.3.1 Compression State
	An endpoint MUST treat a field block that follows an
	acknowledgment of the reduction to the maximum dynamic table size
	as a connection error (Section 5.4.1) of type COMPRESSION_ERROR if
	it does not start with a conformant Dynamic Table Size Update
	instruction.

9113-5.1-1 MUST §5.1 Stream States
	Receiving any frame other than HEADERS or PRIORITY on a stream in
	this state MUST be treated as a connection error (Section 5.4.1)
	of type PROTOCOL_ERROR.

9113-5.1-2 MUST §5.1 Stream States
	If this stream is initiated by the server, as described in Section
	5.1.1, then receiving a HEADERS frame MUST also be treated as a
	connection error (Section 5.4.1) of type PROTOCOL_ERROR.

9113-5.1-3 MUST_NOT §5.1 Stream States
	An endpoint MUST NOT send any type of frame other than HEADERS,
	RST_STREAM, or PRIORITY in this state.
	n/a client: requirement on servers
	n/a server: the Go server doesn't implement server push

9113-5.1-4 MAY §5.1 Stream States
	A PRIORITY or WINDOW_UPDATE frame MAY be received in this state.
	n/a client: requirement on servers
	n/a server: the Go server doesn't implement server push

9113-5.1-5 MUST §5.1 Stream States
	Receiving any type of frame other than RST_STREAM, PRIORITY, or
	WINDOW_UPDATE on a stream in this state MUST be treated as a
	connection error (Section 5.4.1) of type PROTOCOL_ERROR.
	n/a client: requirement on servers
	n/a server: the Go server doesn't implement server push

9113-5.1-6 MUST_NOT §5.1 Stream States
	An endpoint MUST NOT send any type of frame other than RST_STREAM,
	WINDOW_UPDATE, or PRIORITY in this state.
	n/a client: the Go client disables server push (SETTINGS_ENABLE_PUSH=0) and treats any PUSH_PROMISE as a connection error (9113-6.6-9)
	n/a server: requirement on clients

9113-5.1-7 MUST §5.1 Stream States
	Receiving any type of frame other than HEADERS, RST_STREAM, or
	PRIORITY on a stream in this state MUST be treated as a connection
	error (Section 5.4.1) of type PROTOCOL_ERROR.
	n/a client: the Go client disables server push (SETTINGS_ENABLE_PUSH=0) and treats any PUSH_PROMISE as a connection error (9113-6.6-9)
	n/a server: requirement on clients

9113-5.1-8 MUST §5.1 Stream States
	If an endpoint receives additional frames, other than
	WINDOW_UPDATE, PRIORITY, or RST_STREAM, for a stream that is in
	this state, it MUST respond with a stream error (Section 5.4.2) of
	type STREAM_CLOSED.
	n/a client: the Go client resets its request stream (RST_STREAM NO_ERROR) when the response ends while it is still sending, so it doesn't remain half-closed (remote)

9113-5.1-9 MUST_NOT §5.1 Stream States
	An endpoint MUST NOT send frames other than PRIORITY on a closed
	stream.

9113-5.1-10 MAY §5.1 Stream States
	An endpoint MAY treat receipt of any other type of frame on a
	closed stream as a connection error (Section 5.4.1) of type
	STREAM_CLOSED, except as noted below.
	n/a client: permission (MAY); there is no behavior to require
	n/a server: permission (MAY); there is no behavior to require

9113-5.1-11 MUST §5.1 Stream States
	An endpoint MUST minimally process and then discard any frames it
	receives in this state.

9113-5.1-12 MAY §5.1 Stream States
	Endpoints MAY use other signals to detect that a peer has received
	the frames that caused the stream to enter the "closed" state and
	treat receipt of any frame other than PRIORITY as a connection
	error (Section 5.4.1) of type PROTOCOL_ERROR.
	n/a client: permission (MAY); there is no behavior to require
	n/a server: permission (MAY); there is no behavior to require

9113-5.1-13 SHOULD_NOT §5.1 Stream States
	Endpoints SHOULD NOT use timers for this purpose.
	n/a client: internal implementation choice, not observable
	n/a server: internal implementation choice, not observable

9113-5.1-14 SHOULD §5.1 Stream States
	In the absence of more specific rules, implementations SHOULD
	treat the receipt of a frame that is not expressly permitted in
	the description of a state as a connection error (Section 5.4.1)
	of type PROTOCOL_ERROR.

9113-5.1.1-1 MUST §5.1.1 Stream Identifiers
	Streams initiated by a client MUST use odd-numbered stream
	identifiers; those initiated by the server MUST use even-numbered
	stream identifiers.

9113-5.1.1-2 MUST §5.1.1 Stream Identifiers
	The identifier of a newly established stream MUST be numerically
	greater than all streams that the initiating endpoint has opened
	or reserved.

9113-5.1.1-3 MUST §5.1.1 Stream Identifiers
	An endpoint that receives an unexpected stream identifier MUST
	respond with a connection error (Section 5.4.1) of type
	PROTOCOL_ERROR.

9113-5.1.2-1 MUST_NOT §5.1.2 Stream Concurrency
	Endpoints MUST NOT exceed the limit set by their peer.

9113-5.1.2-2 MUST §5.1.2 Stream Concurrency
	An endpoint that receives a HEADERS frame that causes its
	advertised concurrent stream limit to be exceeded MUST treat this
	as a stream error (Section 5.4.2) of type PROTOCOL_ERROR or
	REFUSED_STREAM.
	n/a client: servers open streams only by server push, which the Go client disables

9113-5.2.1-1 MAY §5.2.1 Flow-Control Principles
	A receiver MAY choose to set any window size that it desires for
	each stream and for the entire connection.
	n/a client: permission (MAY); there is no behavior to require
	n/a server: permission (MAY); there is no behavior to require

9113-5.2.1-2 MUST §5.2.1 Flow-Control Principles
	A sender MUST respect flow-control limits imposed by a receiver.

9113-5.2.2-1 MUST §5.2.2 Appropriate Use of Flow Control
	Endpoints MUST read and process HTTP/2 frames from the TCP receive
	buffer as soon as data is available.

9113-5.3.2-1 SHOULD §5.3.2 Priority Signaling in This Document
	Servers SHOULD use other contextual information in determining
	priority of requests in the absence of any priority signals.
	n/a client: requirement on servers
	n/a server: scheduling policy, not reliably observable by an interop test

9113-5.3.2-2 MAY §5.3.2 Priority Signaling in This Document
	Servers MAY interpret the complete absence of signals as an
	indication that the client has not implemented the feature.
	n/a client: permission (MAY); there is no behavior to require
	n/a server: permission (MAY); there is no behavior to require

9113-5.4-1 MAY,SHOULD §5.4 Error Handling
	Implementations MAY discover multiple errors during processing,
	but they SHOULD report at most one stream and one connection error
	as a result.

9113-5.4-2 SHOULD §5.4 Error Handling
	In comparison, the protocol permits multiple GOAWAY frames, though
	an endpoint SHOULD report just one type of connection error unless
	an error is encountered during graceful shutdown.

9113-5.4-3 MAY §5.4 Error Handling
	If this occurs, an endpoint MAY send an additional GOAWAY frame
	with the new error code, in addition to any prior GOAWAY that
	contained NO_ERROR.
	n/a client: permission (MAY); there is no behavior to require
	n/a server: permission (MAY); there is no behavior to require

9113-5.4-4 MAY §5.4 Error Handling
	If an endpoint detects multiple different errors, it MAY choose to
	report any one of those errors.
	n/a client: permission (MAY); there is no behavior to require
	n/a server: permission (MAY); there is no behavior to require

9113-5.4-5 MUST §5.4 Error Handling
	If a frame causes a connection error, that error MUST be reported.

9113-5.4-6 MAY §5.4 Error Handling
	Additionally, an endpoint MAY use any applicable error code when
	it detects an error condition; a generic error code (such as
	PROTOCOL_ERROR or INTERNAL_ERROR) can always be used in place of
	more specific error codes.
	n/a client: permission (MAY); there is no behavior to require
	n/a server: permission (MAY); there is no behavior to require

9113-5.4.1-1 SHOULD §5.4.1 Connection Error Handling
	An endpoint that encounters a connection error SHOULD first send a
	GOAWAY frame (Section 6.8) with the stream identifier of the last
	stream that it successfully received from its peer.

9113-5.4.1-2 MUST §5.4.1 Connection Error Handling
	After sending the GOAWAY frame for an error condition, the
	endpoint MUST close the TCP connection.

9113-5.4.1-3 MAY §5.4.1 Connection Error Handling
	In particular, an endpoint MAY choose to treat a stream error as a
	connection error.
	n/a client: permission (MAY); there is no behavior to require
	n/a server: permission (MAY); there is no behavior to require

9113-5.4.1-4 SHOULD §5.4.1 Connection Error Handling
	Endpoints SHOULD send a GOAWAY frame when ending a connection,
	providing that circumstances permit it.

9113-5.4.2-1 MUST §5.4.2 Stream Error Handling
	The peer that sends the RST_STREAM frame MUST be prepared to
	receive any frames that were sent or enqueued for sending by the
	remote peer.

9113-5.4.2-2 SHOULD_NOT §5.4.2 Stream Error Handling
	Normally, an endpoint SHOULD NOT send more than one RST_STREAM
	frame for any stream.

9113-5.4.2-3 MAY §5.4.2 Stream Error Handling
	However, an endpoint MAY send additional RST_STREAM frames if it
	receives frames on a closed stream after more than a round-trip
	time.
	n/a client: permission (MAY); there is no behavior to require
	n/a server: permission (MAY); there is no behavior to require

9113-5.4.2-4 MUST_NOT §5.4.2 Stream Error Handling
	To avoid looping, an endpoint MUST NOT send a RST_STREAM in
	response to a RST_STREAM frame.

9113-5.5-1 MUST §5.5 Extending HTTP/2
	Implementations MUST ignore unknown or unsupported values in all
	extensible protocol elements.

9113-5.5-2 MUST §5.5 Extending HTTP/2
	Implementations MUST discard frames that have unknown or
	unsupported types.

9113-5.5-3 MUST §5.5 Extending HTTP/2
	However, extension frames that appear in the middle of a field
	block (Section 4.3) are not permitted; these MUST be treated as a
	connection error (Section 5.4.1) of type PROTOCOL_ERROR.

9113-5.5-4 SHOULD §5.5 Extending HTTP/2
	Extensions SHOULD avoid changing protocol elements defined in this
	document or elements for which no extension mechanism is defined.
	n/a client: requirement on the design of extensions
	n/a server: requirement on the design of extensions

9113-5.5-5 MUST §5.5 Extending HTTP/2
	An extension that changes existing protocol elements or state MUST
	be negotiated before being used.

9113-5.5-6 MUST §5.5 Extending HTTP/2
	If a setting is used for extension negotiation, the initial value
	MUST be defined in such a fashion that the extension is initially
	disabled.
	n/a client: requirement on the design of extensions
	n/a server: requirement on the design of extensions

9113-6.1-1 MAY §6.1 DATA
	DATA frames MAY also contain padding.

9113-6.1-2 MUST §6.1 DATA
	Padding octets MUST be set to zero when sending.

9113-6.1-3 MAY §6.1 DATA
	A receiver is not obligated to verify padding but MAY treat non-
	zero padding as a connection error (Section 5.4.1) of type
	PROTOCOL_ERROR.
	n/a client: permission (MAY); there is no behavior to require
	n/a server: permission (MAY); there is no behavior to require

9113-6.1-4 MUST §6.1 DATA
	DATA frames MUST be associated with a stream.

9113-6.1-5 MUST §6.1 DATA
	If a DATA frame is received whose Stream Identifier field is 0x00,
	the recipient MUST respond with a connection error (Section 5.4.1)
	of type PROTOCOL_ERROR.

9113-6.1-6 MUST §6.1 DATA
	If a DATA frame is received whose stream is not in the "open" or
	"half-closed (local)" state, the recipient MUST respond with a
	stream error (Section 5.4.2) of type STREAM_CLOSED.

9113-6.1-7 MUST §6.1 DATA
	If the length of the padding is the length of the frame payload or
	greater, the recipient MUST treat this as a connection error
	(Section 5.4.1) of type PROTOCOL_ERROR.

9113-6.2-1 MUST §6.2 HEADERS
	Padding octets MUST be set to zero when sending.

9113-6.2-2 MAY §6.2 HEADERS
	A receiver is not obligated to verify padding but MAY treat non-
	zero padding as a connection error (Section 5.4.1) of type
	PROTOCOL_ERROR.
	n/a client: permission (MAY); there is no behavior to require
	n/a server: permission (MAY); there is no behavior to require

9113-6.2-3 MUST §6.2 HEADERS
	A HEADERS frame without the END_HEADERS flag set MUST be followed
	by a CONTINUATION frame for the same stream.

9113-6.2-4 MUST §6.2 HEADERS
	A receiver MUST treat the receipt of any other type of frame or a
	frame on a different stream as a connection error (Section 5.4.1)
	of type PROTOCOL_ERROR.

9113-6.2-5 MUST §6.2 HEADERS
	HEADERS frames MUST be associated with a stream.

9113-6.2-6 MUST §6.2 HEADERS
	If a HEADERS frame is received whose Stream Identifier field is
	0x00, the recipient MUST respond with a connection error (Section
	5.4.1) of type PROTOCOL_ERROR.

9113-6.2-7 MUST §6.2 HEADERS
	If the length of the padding is the length of the frame payload or
	greater, the recipient MUST treat this as a connection error
	(Section 5.4.1) of type PROTOCOL_ERROR.

9113-6.3-1 MUST §6.3 PRIORITY
	If a PRIORITY frame is received with a stream identifier of 0x00,
	the recipient MUST respond with a connection error (Section 5.4.1)
	of type PROTOCOL_ERROR.

9113-6.3-2 MUST §6.3 PRIORITY
	A PRIORITY frame with a length other than 5 octets MUST be treated
	as a stream error (Section 5.4.2) of type FRAME_SIZE_ERROR.

9113-6.4-1 MUST_NOT §6.4 RST_STREAM
	After receiving a RST_STREAM on a stream, the receiver MUST NOT
	send additional frames for that stream, except for PRIORITY.

9113-6.4-2 MUST §6.4 RST_STREAM
	However, after sending the RST_STREAM, the sending endpoint MUST
	be prepared to receive and process additional frames sent on the
	stream that might have been sent by the peer prior to the arrival
	of the RST_STREAM.

9113-6.4-3 MUST §6.4 RST_STREAM
	RST_STREAM frames MUST be associated with a stream.

9113-6.4-4 MUST §6.4 RST_STREAM
	If a RST_STREAM frame is received with a stream identifier of
	0x00, the recipient MUST treat this as a connection error (Section
	5.4.1) of type PROTOCOL_ERROR.

9113-6.4-5 MUST_NOT §6.4 RST_STREAM
	RST_STREAM frames MUST NOT be sent for a stream in the "idle"
	state.

9113-6.4-6 MUST §6.4 RST_STREAM
	If a RST_STREAM frame identifying an idle stream is received, the
	recipient MUST treat this as a connection error (Section 5.4.1) of
	type PROTOCOL_ERROR.

9113-6.4-7 MUST §6.4 RST_STREAM
	A RST_STREAM frame with a length other than 4 octets MUST be
	treated as a connection error (Section 5.4.1) of type
	FRAME_SIZE_ERROR.

9113-6.5-1 MAY,MUST §6.5 SETTINGS
	A SETTINGS frame MUST be sent by both endpoints at the start of a
	connection and MAY be sent at any other time by either endpoint
	over the lifetime of the connection.

9113-6.5-2 MUST §6.5 SETTINGS
	Implementations MUST support all of the settings defined by this
	specification.

9113-6.5-3 MUST §6.5 SETTINGS
	When this bit is set, the frame payload of the SETTINGS frame MUST
	be empty.

9113-6.5-4 MUST §6.5 SETTINGS
	Receipt of a SETTINGS frame with the ACK flag set and a length
	field value other than 0 MUST be treated as a connection error
	(Section 5.4.1) of type FRAME_SIZE_ERROR.

9113-6.5-5 MUST §6.5 SETTINGS
	The stream identifier for a SETTINGS frame MUST be zero (0x00).

9113-6.5-6 MUST §6.5 SETTINGS
	If an endpoint receives a SETTINGS frame whose Stream Identifier
	field is anything other than 0x00, the endpoint MUST respond with
	a connection error (Section 5.4.1) of type PROTOCOL_ERROR.

9113-6.5-7 MUST §6.5 SETTINGS
	A badly formed or incomplete SETTINGS frame MUST be treated as a
	connection error (Section 5.4.1) of type PROTOCOL_ERROR.

9113-6.5-8 MUST §6.5 SETTINGS
	A SETTINGS frame with a length other than a multiple of 6 octets
	MUST be treated as a connection error (Section 5.4.1) of type
	FRAME_SIZE_ERROR.

9113-6.5.2-1 MUST_NOT §6.5.2 Defined Settings
	A server MUST NOT send a PUSH_PROMISE frame if it receives this
	parameter set to a value of 0; see Section 8.4.
	n/a client: requirement on servers

9113-6.5.2-2 MUST §6.5.2 Defined Settings
	A client that has both set this parameter to 0 and had it
	acknowledged MUST treat the receipt of a PUSH_PROMISE frame as a
	connection error (Section 5.4.1) of type PROTOCOL_ERROR.
	n/a server: requirement on clients

9113-6.5.2-3 MUST §6.5.2 Defined Settings
	Any value other than 0 or 1 MUST be treated as a connection error
	(Section 5.4.1) of type PROTOCOL_ERROR.

9113-6.5.2-4 MUST_NOT §6.5.2 Defined Settings
	A server MUST NOT explicitly set this value to 1.
	n/a client: requirement on servers

9113-6.5.2-5 MAY,MUST §6.5.2 Defined Settings
	A server MAY choose to omit this setting when it sends a SETTINGS
	frame, but if a server does include a value, it MUST be 0.
	n/a client: requirement on servers

9113-6.5.2-6 MUST §6.5.2 Defined Settings
	A client MUST treat receipt of a SETTINGS frame with
	SETTINGS_ENABLE_PUSH set to 1 as a connection error (Section
	5.4.1) of type PROTOCOL_ERROR.
	n/a server: requirement on clients

9113-6.5.2-7 SHOULD_NOT §6.5.2 Defined Settings
	A value of 0 for SETTINGS_MAX_CONCURRENT_STREAMS SHOULD NOT be
	treated as special by endpoints.
	n/a server: a client's SETTINGS_MAX_CONCURRENT_STREAMS limits only server-initiated (push) streams, which the Go server doesn't open

9113-6.5.2-8 SHOULD §6.5.2 Defined Settings
	Servers SHOULD only set a zero value for short durations; if a
	server does not wish to accept requests, closing the connection is
	more appropriate.
	n/a client: requirement on servers
	n/a server: the Go server never advertises SETTINGS_MAX_CONCURRENT_STREAMS=0

9113-6.5.2-9 MUST §6.5.2 Defined Settings
	Values above the maximum flow-control window size of 2^31-1 MUST
	be treated as a connection error (Section 5.4.1) of type
	FLOW_CONTROL_ERROR.

9113-6.5.2-10 MUST §6.5.2 Defined Settings
	The value advertised by an endpoint MUST be between this initial
	value and the maximum allowed frame size (2^24-1 or 16,777,215
	octets), inclusive.

9113-6.5.2-11 MUST §6.5.2 Defined Settings
	Values outside this range MUST be treated as a connection error
	(Section 5.4.1) of type PROTOCOL_ERROR.

9113-6.5.2-12 MAY §6.5.2 Defined Settings
	For any given request, a lower limit than what is advertised MAY
	be enforced.
	n/a client: permission (MAY); there is no behavior to require
	n/a server: permission (MAY); there is no behavior to require

9113-6.5.2-13 MUST §6.5.2 Defined Settings
	An endpoint that receives a SETTINGS frame with any unknown or
	unsupported identifier MUST ignore that setting.

9113-6.5.3-1 MUST §6.5.3 Settings Synchronization
	In order to provide such synchronization timepoints, the recipient
	of a SETTINGS frame in which the ACK flag is not set MUST apply
	the updated settings as soon as possible upon receipt.

9113-6.5.3-2 MUST §6.5.3 Settings Synchronization
	The values in the SETTINGS frame MUST be processed in the order
	they appear, with no other frame processing between values.

9113-6.5.3-3 MUST §6.5.3 Settings Synchronization
	Unsupported settings MUST be ignored.

9113-6.5.3-4 MUST §6.5.3 Settings Synchronization
	Once all values have been processed, the recipient MUST
	immediately emit a SETTINGS frame with the ACK flag set.

9113-6.5.3-5 MAY §6.5.3 Settings Synchronization
	If the sender of a SETTINGS frame does not receive an
	acknowledgment within a reasonable amount of time, it MAY issue a
	connection error (Section 5.4.1) of type SETTINGS_TIMEOUT.
	n/a client: permission (MAY); there is no behavior to require
	n/a server: permission (MAY); there is no behavior to require

9113-6.6-1 MUST §6.6 PUSH_PROMISE
	The promised stream identifier MUST be a valid choice for the next
	stream sent by the sender (see "new stream identifier" in Section
	5.1.1).
	n/a client: requirement on clients
	n/a server: the Go server doesn't implement server push (the validator checks pushes)

9113-6.6-2 MUST §6.6 PUSH_PROMISE

9113-8.2-1 MUST §8.2 HTTP Fields
	Field names MUST be converted to lowercase when constructing an
	HTTP/2 message.

9113-8.2.1-1 SHOULD §8.2.1 Field Validity
	HTTP/2 implementations SHOULD validate field names and values
	according to their definitions in Sections 5.1 and 5.5 of [HTTP],
	respectively, and treat messages that contain prohibited
	characters as malformed (Section 8.1.1).

9113-8.2.1-2 MUST §8.2.1 Field Validity
	Implementations MUST perform the following minimal validation of
	field names and values:

9113-8.2.1-3 MUST_NOT §8.2.1 Field Validity

	0x00-0x20, 0x41-0x5a, or 0x7f-0xff (all ranges inclusive).

9113-8.2.1-4 MUST_NOT §8.2.1 Field Validity
	*  With the exception of pseudo-header fields (Section 8.3), which
	have a name that starts with a single colon, field names MUST NOT

9113-8.2.1-5 MUST_NOT §8.2.1 Field Validity

9113-8.2.1-6 MUST_NOT §8.2.1 Field Validity
	*  A field value MUST NOT start or end with an ASCII whitespace
	character (ASCII SP or HTAB, 0x20 or 0x09).

9113-8.2.1-7 MUST §8.2.1 Field Validity

	these conditions MUST be treated as malformed (Section 8.1.1).

9113-8.2.1-8 MUST_NOT §8.2.1 Field Validity
	In particular, an intermediary that does not process fields when

	n/a client: requirement on intermediaries; the Go client and server are endpoints
	n/a server: requirement on intermediaries; the Go client and server are endpoints

9113-8.2.1-9 SHOULD §8.2.1 Field Validity

# Descriptive requirements.

# descriptions of the protocol, but still constrain implementations.

# DESCRIPTIVE. The text quotes the RFC.

9113-3.4-d1 DESCRIPTIVE §3.4 HTTP/2 Connection Preface
	The client sends the client connection preface as the first
	application data octets of a connection.
	n/a server: requirement on clients

9113-3.4-d2 DESCRIPTIVE §3.4 HTTP/2 Connection Preface
	To avoid unnecessary latency, clients are permitted to send
	additional frames to the server immediately after sending the
	client connection preface, without waiting to receive the server
	connection preface.
	n/a client: permission for clients (the Go client does send requests before receiving the server's preface; servers accepting that is 9113-3.4-d2 server)

9113-4.3-d1 DESCRIPTIVE §4.3 Field Section Compression and Decompression
	An endpoint receiving HEADERS, PUSH_PROMISE, or CONTINUATION
	frames needs to reassemble field blocks and perform decompression
	even if the frames are to be discarded.

9113-4.3.1-d1 DESCRIPTIVE §4.3.1 Compression State
	Any change to the maximum value set using
	SETTINGS_HEADER_TABLE_SIZE takes effect when the endpoint
	acknowledges settings (Section 6.5.3).

9113-5.1-d1 DESCRIPTIVE §5.1 Stream States
	An endpoint that sends a RST_STREAM frame on a stream that is in
	the "open" or "half-closed (local)" state could receive any type
	of frame. The peer might have sent or enqueued for sending these
	frames before processing the RST_STREAM frame. This means updating
	header compression state for HEADERS and PUSH_PROMISE frames.
	Additionally, the content of DATA frames counts toward the
	connection flow-control window.

9113-5.1.1-d1 DESCRIPTIVE §5.1.1 Stream Identifiers
	When a stream transitions out of the "idle" state, all streams in
	the "idle" state that might have been opened by the peer with a
	lower- valued stream identifier immediately transition to
	"closed". That is, an endpoint may skip a stream identifier, with
	the effect being that the skipped stream is immediately closed.
	n/a client: servers open streams only by server push, which the Go client disables

9113-5.2.1-d1 DESCRIPTIVE §5.2.1 Flow-Control Principles
	Of the frames specified in this document, only DATA frames are
	subject to flow control; all other frame types do not consume
	space in the advertised flow-control window.

9113-5.4.3-d1 DESCRIPTIVE §5.4.3 Connection Termination
	If the TCP connection is closed or reset while streams remain in
	the "open" or "half-closed" states, then the affected streams
	cannot be automatically retried (see Section 8.7 for details).
	n/a server: requirement on clients

9113-6.1-d1 DESCRIPTIVE §6.1 DATA
	The entire DATA frame payload is included in flow control,
	including the Pad Length and Padding fields if present.

9113-6.2-d1 DESCRIPTIVE §6.2 HEADERS
	However, a HEADERS frame with the END_STREAM flag set can be
	followed by CONTINUATION frames on the same stream.

9113-6.3-d1 DESCRIPTIVE §6.3 PRIORITY
	The PRIORITY frame can be sent on a stream in any state, including
	"idle" or "closed".

9113-6.8-d1 DESCRIPTIVE §6.8 GOAWAY
	To deal with this case, the GOAWAY contains the stream identifier
	of the last peer-initiated stream that was or might be processed
	on the sending endpoint in this connection.

9113-6.8-d2 DESCRIPTIVE §6.8 GOAWAY
	If a connection terminates without a GOAWAY frame, the last stream
	identifier is effectively the highest possible stream identifier.
	On streams with lower- or equal-numbered identifiers that were not
	closed completely prior to the connection being closed,
	reattempting requests, transactions, or any protocol activity is
	not possible, except for idempotent actions like HTTP GET, PUT, or
	DELETE.
	n/a server: requirement on clients

9113-6.8-d3 DESCRIPTIVE §6.8 GOAWAY
	Any protocol activity that uses higher-numbered streams can be
	safely retried using a new connection.
	n/a server: requirement on clients

9113-6.9-d1 DESCRIPTIVE §6.9 WINDOW_UPDATE
	WINDOW_UPDATE can be sent by a peer that has sent a frame with the
	END_STREAM flag set. This means that a receiver could receive a
	WINDOW_UPDATE frame on a stream in a "half-closed (remote)" or
	"closed" state.

9113-6.9-d2 DESCRIPTIVE §6.9 WINDOW_UPDATE
	This is necessary even if the frame is in error. The sender counts
	the frame toward the flow-control window, but if the receiver does
	not, the flow-control window at the sender and receiver can become
	different.

9113-6.9.1-d1 DESCRIPTIVE §6.9.1 The Flow-Control Window
	Receivers are advised to have mechanisms in place to avoid sending
	WINDOW_UPDATE frames with very small increments; see Section
	4.2.3.3 of [RFC1122].

9113-6.9.2-d1 DESCRIPTIVE §6.9.2 Initial Flow-Control Window Size
	A SETTINGS frame cannot alter the connection flow-control window.

9113-6.10-d1 DESCRIPTIVE §6.10 CONTINUATION
	Any number of CONTINUATION frames can be sent, as long as the
	preceding frame is on the same stream and is a HEADERS,
	PUSH_PROMISE, or CONTINUATION frame without the END_HEADERS flag
	set.

9113-8.1-d1 DESCRIPTIVE §8.1 HTTP Message Framing
	An HTTP response is complete after the server sends -- or the
	client receives -- a frame with the END_STREAM flag set (including
	any CONTINUATION frames needed to complete a field block).

9113-8.1.1-d1 DESCRIPTIVE §8.1.1 Malformed Messages
	A request or response is also malformed if the value of a content-
	length header field does not equal the sum of the DATA frame
	payload lengths that form the content, unless the message is
	defined as having no content.

9113-8.1.1-d2 DESCRIPTIVE §8.1.1 Malformed Messages
	For example, 204 or 304 responses contain no content, as does the
	response to a HEAD request.

9113-8.3-d1 DESCRIPTIVE §8.3 HTTP Control Data
	Pseudo-header fields are not HTTP header fields.

9113-8.3.1-d1 DESCRIPTIVE §8.3.1 Request Pseudo-Header Fields
	":scheme" is not restricted to "http" and "https" schemed URIs.
	n/a client: the Go client only makes http and https requests

9113-8.3.1-d2 DESCRIPTIVE §8.3.1 Request Pseudo-Header Fields
	All HTTP/2 requests implicitly have a protocol version of "2.0"
	(see Section 6.2 of [HTTP]).

9113-8.5-d1 DESCRIPTIVE §8.5 The CONNECT Method
	After the initial HEADERS frame sent by each peer, all subsequent
	DATA frames correspond to data sent on the TCP connection. The
	END_STREAM flag on a DATA frame is treated as being equivalent to
	the TCP FIN bit.

9113-8.7-d1 DESCRIPTIVE §8.7 Request Reliability
	*  The REFUSED_STREAM error code can be included in a RST_STREAM
	frame to indicate that the stream is being closed prior to any
	processing having occurred. Any request that was sent on the reset
	stream can be safely retried.
	n/a server: requirement on clients

7541-4.1-d1 DESCRIPTIVE §4.1 Calculating Table Size
	The size of an entry is the sum of its name's length in octets (as
	defined in Section 5.2), its value's length in octets, and 32. The
	size of an entry is calculated using the length of its name and
	value without any Huffman encoding applied.

7541-4.2-d1 DESCRIPTIVE §4.2 Maximum Table Size
	The final maximum size is always signaled, resulting in at most
	two dynamic table size updates.

7541-4.3-d1 DESCRIPTIVE §4.3 Entry Eviction When Dynamic Table Size Changes
	Whenever the maximum size for the dynamic table is reduced,
	entries are evicted from the end of the dynamic table until the
	size of the dynamic table is less than or equal to the maximum
	size.

7541-4.4-d1 DESCRIPTIVE §4.4 Entry Eviction When Adding New Entries
	It is not an error to attempt to add an entry that is larger than
	the maximum size; an attempt to add an entry larger than the
	maximum size causes the table to be emptied of all existing
	entries and results in an empty table.

7541-4.4-d2 DESCRIPTIVE §4.4 Entry Eviction When Adding New Entries
	A new entry can reference the name of an entry in the dynamic
	table that will be evicted when adding this new entry into the
	dynamic table.

7541-5.1-d1 DESCRIPTIVE §5.1 Integer Representation
	Otherwise, all the bits of the prefix are set to 1, and the value,
	decreased by 2^N-1, is encoded using a list of one or more octets.

8441-3-d1 DESCRIPTIVE §3 The SETTINGS_ENABLE_CONNECT_PROTOCOL SETTINGS Parameter
	Receipt of this parameter by a server does not have any impact.
	n/a client: requirement on clients
